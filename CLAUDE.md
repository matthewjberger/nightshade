# Nightshade Engine

New to this repo, or starting a fresh session? Run `/intro-nightshade` for a full orientation: the two-layer architecture, where every doc lives, the reference apps to copy, the build/gate workflow, and how to work here without blowing context. The command is source-controlled at `.claude/commands/intro-nightshade.md`.

For games, start with the high-level `nightshade-api` facade. Read `docs/SPEC_RUST_API.md` (the full signature catalog) and the "Start Here" section of `docs/USAGE.md`. The api games `apps/coin_dash` and `apps/coin_rush` and the `template_api/` template are the working references. Reach for the engine layer only when the facade stops covering what you need.

Read `docs/USAGE.md` before writing or modifying engine code (the `nightshade` crate layer).

## Architecture

The crate layering, which crate owns what and the down-only dependency direction Cargo enforces, is documented in `docs/book/src/architecture-overview.md`. This section covers the runtime composition model.

- Programs are plugin-composed: `App::new().add_plugins(DefaultPlugins).add_plugin(MyGamePlugin).run()`. A `Plugin`'s `build(&self, app: &mut App)` registers member worlds, resources (`app.insert_resource`), and systems onto the `Stage` enum (`Stage::Startup` runs once, then every frame the game stages `Stage::First`, `Stage::Update`, `Stage::LateUpdate` run, followed by the engine frame stages `Stage::FrameStart`, `Stage::FrameUpdate`, `Stage::FramePostUpdate`, `Stage::Render`, `Stage::Last`); game logic goes in `Stage::Update`. `app.add_system(stage, system)` is the one registration method: it takes plain `fn(&mut World)` systems, state-and-world `fn(&mut T, &mut World)` game systems (`game_scope` applied at registration), or tuples mixing both; `Stage::Startup` routes to the startup schedule. App-level states drive screen flow: `app.insert_state(Screen::Title)` plus `on_enter`/`on_exit` hooks and the `while_in(state, system)` gate; transitions requested with `next_state(world, ...)` apply at the start of the next frame, and `in_state`/`current_state` read them (sandbox's title/pause/in-game screens are the live example). An empty App does nothing; `WindowPlugin` adds the window, `RenderPlugin` the renderer (hidden window when `WindowPlugin` is omitted), `UiPlugin` the retained UI; `DefaultPlugins` bundles them. Capability plugins bring their own systems and are added explicitly: `AudioPlugin` (opens the device, installs the audio systems), `GamepadPlugin` (polls pads), `PhysicsPlugin` (installs the step, `physics.enabled` stays the pause switch), `CutscenePlugin` (auto-advances playback), `CameraControllerPlugin` (drives the active camera, orbit or fly by component), `ExitOnEscapePlugin`, `TerrainPlugin` (collider tiles window around the `TerrainColliderAnchor` tag), `EguiPlugin`, `SteamPlugin`, `LogPlugin` (in `DefaultPlugins`, owns the tracing subscribers); a capability the program never composes costs nothing. Each plugin's code lives self-contained under `src/plugins/<name>` (systems, components, resources, plugin struct), crate-shaped on purpose but feature-gated into the nightshade crate; `src/ecs/` holds only the core. `App::set_runner` lets a plugin own the main loop itself: `nightshade_api::offscreen::WorkerHostPlugin` hosts the composed App inside a web worker this way (the editor, playground, and self_assembling workers compose it), paired on the page with `nightshade_api::web::use_engine`/`use_engine_typed` and `EngineViewport`. The `State` trait remains as the low-level escape hatch under `App::into_parts` for custom runners.
- ECS via `nightshade_ecs::dynamic` (no `ecs!` macro in the engine). `World { ecs: DynEcs, resources: Resources }` with two member worlds: `world.ecs.worlds[CORE]` (scene) and `world.ecs.worlds[UI]` (retained UI), declared with `nightshade_ecs::dynamic_worlds!`. Components register eagerly in declaration order in `src/ecs/world.rs` (`nightshade_ecs::dynamic_schema!`), which also emits the bitflag constants (`CAMERA | LOCAL_TRANSFORM | GLOBAL_TRANSFORM`); registration order is the schema, never reorder it.
- Typed access is group-routed: `world.get::<Camera>(entity)` / `world.get_mut::<T>` / `world.set(entity, value)` / `world.has::<T>` resolve the owning member world per component type (get_mut and set stamp change ticks; set never registers a type lazily, placement is a schema decision). Group operations (spawn_count, spawn_with, despawn_entities, despawn_recursive, is_alive) are on `world` directly through deref to `DynEcs`; `world.spawn_with((component, ...))` is the default single-entity spawn, deriving the archetype from the component types (bundles can span member worlds), with mask spawn (`spawn_entities`) for batches and all-default rows. Member indexing (`world.ecs.worlds[CORE]`) remains for world-level operations: pinned per-world queries, ticks, structural logs, raw table passes, snapshots. `world.resources` for singletons grouped into domain sub-structs (`physics`, `input`, `assets`, `text`, `loading`, `transform_state`, `cleanup`, `entities`, `commands`, `schedules`, etc.).
- Most engine systems run automatically in the frame stages (`Stage::FrameStart`, `Stage::FrameUpdate`, `Stage::FramePostUpdate`, `Stage::Render`, `Stage::Last`) that follow the game stages each frame in one `Stages` run: the core systems (animation, transforms, input) land first and each composed plugin registers its own (physics, navmesh, retained UI, render sync) with `app.add_system(Stage::..., system)`; within a stage, systems run in registration order. Don't call these manually.
- Camera controllers are opt-in: call `fly_camera_system(world)` or `pan_orbit_camera_system(world)` from your update system. `fly_camera_system` skips if the active camera has `PAN_ORBIT_CAMERA`.
- Scenes load from glTF. Find entities by name after spawning (`world.ecs.worlds[CORE].find_entity_by_name`).
- `apps/sandbox` is the go-to reference for an idiomatic engine-level 3D game (when you have dropped below the `nightshade-api` facade). Read it before writing a new engine-layer app: a game plugin added in the App builder registering startup and update systems over game_scope, an app member world for game components, screen lifecycle in `systems/lifecycle.rs`, retained UI handles stored in a plain resources struct, `theme.rs` for UI constants, prototype textures, level load/save. The `template/` crate is the same architecture in skeleton form.

## Querying

- Default: typed tuple queries. `world.query_ref::<(&Cloth, &RenderMesh)>().iter()` for reads (a real iterator on `&world`, never registers types), `query::<(&mut A, &B)>().for_each(...)` for writes (`&mut` elements stamp change ticks per visited row, so take `&mut` only for what you actually write). Filters: `.with::<T>()` / `.without::<T>()` / `.with_mask(MASK)` / `.without_mask(MASK)` / `.changed::<T>()` / `.added::<T>()`. Up to eight elements, `Option<&T>` for optional presence.
- Bulk visit-don't-write passes stay on the raw tier (`for_each_mut(MASK, 0, |entity, table, idx| ...)` with `table.column_mut(key)`, keys from `register::<T>()`), which does not stamp ticks; pair with explicit side-channel marks or `mark_changed`/`mark_columns_changed`.
- Entity-only iteration: `query_entities(MASK)` (allocation-free iterator).
- For structural mutations during iteration (add/remove components, despawn, set component triggering archetype migration), use the two-pass pattern: gather into a small `Vec` of `(entity, payload)` tuples, then a second loop that applies the mutations.
- Two command queues at `world.resources.commands`: `commands.ecs` (DespawnRecursive, ReloadMaterial) is drained by `process_commands_system` in the frame schedule. `commands.render` (texture uploads, HDR skybox, IBL captures, screenshot) is drained by the renderer at frame setup. Push via `queue_ecs_command(world, EcsCommand::...)` or `queue_render_command(world, RenderCommand::...)` (free fns in the prelude, not methods).

## App Member-World Pattern

Games put their components in a third member world of the engine group, sharing entity identity with the render entities. In the app's `ecs.rs`: `nightshade_ecs::dynamic_schema! { pub fn register_<app>_components { field: Type => CONST, } }`, registered once at initialize with `world.ecs.add_world_at(GAME, register_<app>_components());` (`GAME` is the prelude's first-app-member index). Game state is set directly on the engine entity (`world.set(entity, component)` routes to the member world and creates the row), read back with routed typed queries, and one recursive despawn tears down render and game state together (group despawn retires rows in every member world). App-wide state lives in a plain resources struct owned by the app's `State` type, not in an ECS world. There is no link component and no position sync pass; write `LocalTransform` through `world.get_mut` directly. Marker tags (selection, locked, in-hand) are group-level: `world.add_tag_type::<T>(entity)` / `remove_tag_type` / `has_tag_type` / `query_tag_type` (lazy registration, no mask bits, dropped on group despawn); filter typed queries with `.with_tag_set(world.ecs.tag_set_type::<T>()...)`. Tuples spanning member worlds (game state plus a core transform) run through `world.ecs.query_join::<(...)>()`: the world holding every mutable element drives, foreign elements read per entity, so mutate your own state, read theirs, and collect foreign writes for a second pass. See `apps/mini_dungeon` or `apps/tower_defense` for live examples and `template/` for the skeleton.

## Gotchas

- WGSL uniform structs need 16-byte alignment. Use `vec4` packing, not `vec3`.
- `nalgebra_glm` only, never `glam`. `Vec2::component_mul()` for element-wise multiply.
- The renderer syncs by diffing nightshade_ecs change ticks, and raw-tier table writes (`for_each_mut`, `for_each_tables_mut`, `column_mut`) do not stamp them. Write every render-facing component (transforms, visibility, lights, morph weights, text, water, decals, instanced meshes) through the stamping paths (`set`, `get_mut::<T>`, or `&mut` typed-query elements) or the change never reaches the renderer. Raw-tier bulk passes can opt in afterward with `world.ecs.worlds[CORE].mark_changed(entity, MASK)` or per-table `table.mark_columns_changed(MASK, tick)`. Mutate registered materials through `material_registry_mutate`, never through `registry_entry_by_name_mut`.
- `nightshade_ecs::Entity` is the entity type everywhere.
- Sprite atlas slot size: `nightshade::render::SPRITE_ATLAS_SLOT_SIZE` = (512, 512).
