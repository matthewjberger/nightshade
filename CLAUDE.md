# Nightshade Engine

New to this repo, or starting a fresh session? Run `/intro-nightshade` for a full orientation: the architecture, the reference apps to copy, the build/gate workflow, and how to work here without blowing context. The commands are source-controlled at `.claude/commands/`, which also holds `/new-game` to start a game and `/grow-game` to grow one past its vertical slice.

`apps/games/tower_defense` and the `template/` crate are the working references, with `apps/games/coin_dash`, `apps/games/coin_rush`, and `apps/features/picking` as smaller ones. `apps/rendering/` holds one app for each capability of the renderer, each laid out like `template/` and showing one feature over a Khronos sample model and nothing else; they open on wgpu and take `--no-default-features --features vulkan` to open on the other backend. `apps/vulkan/` holds the three that only Vulkan can draw, mesh shaders and the two ray-traced ones. `apps/games/multiplayer/` holds the apps that cannot run alone, and `apps/games/multiplayer/sandbox` is the one there: a shared world where the copy that starts first plays and serves, or serves alone with `--serve`. It sits one level below the other games, so it is named on its own line in the workspace `members` and the three recipes that read `apps` two levels deep. `crates/plugins/domain/nightshade-gamepad` is the model for a capability crate, and `crates/plugins/domain/nightshade-physics` is the model for one that depends on another.

## Working here

This is a private solo project, so this file, the notes at `docs/notes/`, and the commands at `.claude/commands/` carry everything an agent needs. Read `docs/notes/README.md` first and open the notes that touch what you are about to change: they are the traps that cost a day each to find. `docs/antipatterns.md` lists the shapes this repo refuses, and `docs/writing-directive.md` is the authority for prose. When you learn something durable, write a note and add its line to the index.

**Rust.** No comments, ever, rustdoc included, and `just lint-dag` fails on one. No debug logging. No abbreviations, so `index` rather than `i`. No `unsafe` unless the task asks for it. No `mod.rs`, the 2024 edition layout only. No `#[allow(clippy::...)]`, fix the lint instead. `nalgebra_glm` only, never `glam`. Let chains rather than nested `if let`. Never mark something `pub` that nothing outside its module names. Delete the function you replace in the same change, and take the helpers, types, imports and constants that only it used.

**How to work.** Read a whole file before you change it. Copy a pattern the repo already carries rather than inventing one, and look in the reference apps first. Never stand up a dummy implementation, a fallback, or a simpler thing than the one that was asked for. Do not refactor widely unless the task says to. When a library does not behave, your syntax is out of date, so read its current documentation rather than reaching for a different library. Find the cause rather than trying things, and find it by reading the code: do not write a small program to chase a fault, and do not run the app to find one.

**Gates.** `just lint` is the whole gate and CI runs it. Run what your change reaches: `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets -- -D warnings` always, then `just lint-dag` for the crate and module graph, `just lint-examples` when you touch an example under `crates/framework/`, `just lint-features` when you touch a contract, and `just lint-wasm` when the web build reads what you changed. Run `cargo test --lib -p <crate>` for the crates you touched, and never the whole suite unless you were asked for it by name. `just run <app>` builds and runs an app, because `cargo run` misses the flags the recipes carry. Every app takes `--capture <path> --capture-frame <n> --size WxH`, which is the bounded way to put a change on the screen and look at it.

**Commits.** Conventional commits, plain prose, no em-dashes and no semicolons in the message. Never add a Co-Authored-By line, a Signed-off-by line, or any other attribution. Write the message to a file and commit with `git commit -F`, because a here-string leaks characters into the subject. Format, lint and run the reachable tests first, and say which ran and which are stale. Commit and push only when you are asked to.

**The machine.** The owner works on Windows, so some `just` recipes are PowerShell and a pipe of `2>&1` from cargo or just false-fails there. Read a recipe before you trust it on another platform. Every path in this repository's own documents is relative to the repository root. Use `rg` rather than `grep`, and never create a file named `nul`.

**Shape of the code.** No object orientation, and the builder is the only exception. No `Rc<RefCell<T>>`. A component holds one value, so a struct that gathers fields under the name of a thing is an object and an empty marker is the same mistake: `docs/antipatterns.md` is the list, and `/sweep-antipatterns` walks it. Never hand-roll a standard algorithm or utility when a crate carries it, and use the `stateless` crate for a state machine. `#[serde(default)]` goes on the struct, never on a field. An app keeps the bands of `template/`: per-entity data in `components`, shared data in `resources`, tables in `data`, behavior in `systems/<name>.rs`, and helpers in `commands` and `queries`. Never call an engine schedule system by hand to fix an ordering problem, and never write a one-line wrapper that forwards to a function that already exists.

**Never fake completion.** No dummy implementation, no fallback, and never a real code path parked behind a false flag so the work looks finished. Never write a test or offer testing as a hardening step. Say what is done and what is not.

**Verifying.** Reason through the code, as many times as it takes. Never add temporary tracing, never measure at runtime, and never read pixels from a capture as evidence of a fault. Running one app to see a change work is right, a battery of them is not, and the app is driven by the owner: never send it synthetic input. "Evaluate" means read the code. "Sanity check" means reason through it.

**Prose.** `docs/writing-directive.md` is the authority. No em-dashes and no semicolons. Do not write "it is X, not Y". No time estimates. Documentation describes what exists, never what was tried, never a plan, and never a file listing. A game's interface never names a key or a button and never explains itself.

**Git.** The default branch is main. Never use `git revert`. Never run `git subtree push` by hand, because the justfile publish recipes own that. Commit a file that shows only line-ending churn rather than restoring it. Before anything destructive, read the state in its own command: another agent may share this repository, so HEAD may not be yours.

**Pace.** Do the whole thing and land it in one commit rather than planning milestones. Do not stop to report progress, do not defer part of it to a later session, and do not decline by calling the scope too large. Ask only when the answer changes what you would build.

**Rendering.** Be careful with coordinate systems, the Y flip, the reverse-Z depth range, UV mapping and atlas bleeding. Look at the output rather than assuming it.

## Architecture

The crates are `nightshade-ecs`, then `nightshade` on top of it, then the plugin crates on top of `nightshade`. `nightshade` holds no capability and no GPU API: it is three files and holds `App`, `Plugin`, `Stage`, and the `World` it re-exports from `nightshade-ecs`. The window, the input, and the clock are `nightshade-platform`, and the transforms and the hierarchy are `nightshade-scene`, both plugin crates like the rest. `nightshade-render` holds the render description, the data both backends read: materials, meshes, textures, lights, geometry, the render config, the frame description, the per-entity render components, and the registries and caches as state. It carries in `commands` the functions that change those registries and caches, `material_registry_mutate`, `mesh_cache_insert`, `texture_cache_acquire` and `register_primitive_mesh` among them, because a type lives with its functions and five crates outside the renderer call them. It also carries in `queries` the math that is the same whichever backend draws: the reverse-Z projections, the cascade view-projections and frustum tests in `queries/projection.rs`, and `build_render_lighting` in `queries/lights.rs`, which turns the world into the `RenderLighting` both backends read. `queries/lights.rs` also holds the shadow readouts, `cascade_texel_sizes`, `shadows_enabled`, `screen_coverage` and `wanted_slot`, and `queries/probes.rs` works the probe grid out of the shading the world asks for. The caps and the atlas layout are not shared, because a backend picks its own, so those functions take them as parameters, `probe_counts` its grid caps and `wanted_slot` its slot widths among them, and `data/shadow.rs` keeps only the cascade split policy. It also holds the cluster grid and its slicing in `data/config/clusters.rs`, which both backends read so they cannot disagree on it. It has no system and no plugin, so it is a contract crate the way `nightshade-paint` is, with the shared CPU work that both backends would otherwise each write beside it, the image decoding in `data/decoded_image.rs` included, and it names no GPU API, no platform, and no winit. `just lint-dag` checks the GPU half of that and nothing else. `nightshade-graphics` holds what runs over that description: the asset loading, the world spawners, the nine CPU passes, and `GraphicsPlugin` that registers them. It splits at a contract like the rest, so `commands`, `queries`, `resources` and `prelude` are behind `contract` and only `plugin` and `systems` are behind `plugin`. Seven plugin crates take the description and never the pipeline: animation, camera, camera-controller, navmesh, picking, text, and ui name `nightshade-render` and never name `nightshade-graphics`. `nightshade-wgpu` holds the render graph and the substrate every pass draws through, and the geometry passes themselves are `nightshade-wgpu-geometry` at `crates/plugins/draw/`, `nightshade-window` holds the winit runner over it, and three crates name the renderer. Cargo holds that direction. `just lint-dag` reads only the module graph of the engine and plugin crates, and fails on a cycle between top-level modules. It knows nothing about the bands and it reads no app. This section covers the runtime composition model.

- Programs are plugin-composed: `App::new().add_plugins(DefaultPlugins).add_plugin(MyGamePlugin).run()`. A `Plugin`'s `build(&self, app: &mut App)` registers resources (`app.insert_resource`) and systems onto the `Stage` enum (`Stage::Startup` runs once, then every frame the game stages `Stage::First`, `Stage::Update`, `Stage::LateUpdate` run, followed by the engine frame stages `Stage::FrameStart`, `Stage::FrameUpdate`, `Stage::FramePostUpdate`, `Stage::Render`, `Stage::Last`); game logic goes in `Stage::Update`. `app.add_system(stage, system)` is the one registration method: it takes plain `fn(&mut World)` systems and parameter systems taking `Res<T>`, `ResMut<T>`, `Commands`, `&mut Storage`, and up to six `Query<...>` or one query bundle, or tuples mixing them; `Stage::Startup` routes to the startup schedule. A parameter system reports the access read off its signature and can share a batch, while a plain `fn(&mut World)` reaches everything and runs alone. A system's `Commands` queue is not applied on the thread that ran it: the runner parks it on the storage and the schedule drains it on its own thread, right after the system in the sequential path and right after the whole batch in the parallel one, so a queue never moves rows under another system of its batch and command systems still share a batch. A parameter that wraps `Commands` hands both `apply` and `flush` through. There is no whole-map parameter: a system that wants more resources than the slots hold declares a `nightshade_ecs::resource_bundle!`, which names in a `write` band every resource it changes and in a `read` band every one it only reports, and costs one slot however many it holds, the way `query_bundle!` does for queries.
- Batching is on by default (`nightshade-ecs` default features carry `parallel`, native only). Two systems batch when the access their signatures give is disjoint, and a resource both of them only read is disjoint, because `Res<T>` takes a shared slot and `ResMut<T>` an exclusive one. What is left in one batch alone is the plain `fn(&mut World)` shape, which reports exclusive access: `RUST_LOG=nightshade::stages=debug` prints the batches of every stage.
- Almost nothing takes the world any more: outside the runner and the schedule runners, every function names what it touches, as `Res`/`ResMut`/`Query`/`Commands`/`&mut Storage` or, for a plain helper the schedule never sees, as the `&mut Storage` and `&mut ResourceMap` pair. A hook is not a plain helper: a pre-render hook is a system and names its parameters. The nineteen that still take it all run a schedule, which `Schedule<H>::run(&mut H)` requires: the `State` trait's `initialize` and `run_systems`, the runner's frame paths, the offscreen driver, `WindowApp::frame`, `run_retained_ui_schedule`, `run_physics_systems`, and boids_cpu's `step_flock`. `WindowApp::init` takes the rows and the resources, because building an app composes state into them and runs nothing. A system whose queries outgrow the slots takes a bundle declared with `nightshade_ecs::query_bundle!`, which costs one slot however many queries it holds. What stays plain mostly stays for a reason: a system that adds or removes a component migrates archetypes, which conflicts with everything by definition, and the frame is a pipeline whose stages feed each other. Converting a run of neighbors is what moves the count, not converting one system. The other parallelism, per-entity rather than per-system, is already on the GPU: culling is a compute pass over `cull_objects_buffer` and the pose pipeline is GPU driven. What is left on the CPU is a hierarchy walk (transform propagation), a small-N pass that collects as it goes (the animation players), and one-shot work (bounding volumes).
- Within a stage, systems run in registration order unless something states otherwise: `stages.stage_mut(stage.name()).order(earlier, later)` names two systems and holds whichever plugin was composed first, is inert when the schedule does not hold both, and is applied by a stable topological sort on the first run. State an order rather than splicing a system in by name. App-level states drive screen flow: `app.insert_state(Screen::Title)` plus `on_enter`/`on_exit` hooks and the `while_in(state, system)` gate; transitions requested with `next_state(world, ...)` apply at the start of the next frame, and `in_state`/`current_state` read them (tower_defense's screens are the live example).
- An empty App does nothing. Every program composes `DefaultPlugins` of the backend it opens on, which is the window, the command line, the log, that backend and the camera in one group, and the window plugin pulls in `PlatformPlugin`, `ScenePlugin`, and `GraphicsPlugin`. The group lives in `nightshade-window` and is generic over the render plugin, so each backend hands out an alias of it and a program that wants one member different sets that member with `.set(plugin)` rather than composing the five itself. A program that wants the escape key to exit registers `escape_key_exit_system` on `Stage::FrameUpdate`, which is one line and needs no plugin. The retained UI is `UiPlugin`, a crate of its own, composed like any other. Capability plugins bring their own systems and are added explicitly. Every capability is a crate. The `nightshade` crate carries no features at all. The engine is two crates and they sit at `crates/`: `nightshade-ecs` at the bottom, and `nightshade` on top of it and nothing else. Everything else is a plugin crate at `crates/plugins/`, `nightshade-platform` and `nightshade-scene` included. `nightshade` is three files, `app.rs`, `plugin.rs`, and `lib.rs`, so a plugin gets `App`, `Plugin`, and `Stage` and nothing else. There is no `CorePlugin`: `App::new` builds the tracking world, inserts `HierarchyIndex`, and registers the event channel advance, because that is the frame contract rather than a choice a plugin makes. `nightshade-platform` holds the winit window, the input state, the input capture claims, the clock, and `AppEvent`, and it is data the way `nightshade-render` is data: `nightshade-window` owns the winit loop and is the only crate that fills it. `nightshade-scene` holds what a node is and where it is, the name, the visibility, the guid, the transforms, and `ScenePlugin`, which registers the propagation pass. `ChildOf` and `HierarchyIndex` are declared in `nightshade-ecs`, so the parent-child tree is ECS storage and `nightshade-scene` is the crate that composes matrices over it. There is one `World` and it is `nightshade_ecs::World`, which `nightshade` re-exports: the substrate wraps nothing, so a system that wants the rows and the resources takes `&mut Storage` or reads them off the world directly, and `world.ecs` is gone. A capability that wants the window or the input names `nightshade-platform` directly, and one that wants a transform or a name names `nightshade-scene`. Each of those crates carries its own prelude, so a file writes `use nightshade::prelude::*` for `App` and the system parameters, and adds `use nightshade_platform::prelude::*` or `use nightshade_scene::prelude::*` for what it actually reads. The substrate prelude carries the vocabulary the engine picked and nothing else it does not own: `nalgebra_glm` with `Mat4`, `Quat` and the vectors, and `Duration`, `Instant`, `SystemTime` and `UNIX_EPOCH` from `web-time`. A crate that logs, reads JSON, or speaks to the browser declares that dependency itself. There is no engine event crate and no engine event enum: the bus is `nightshade_ecs::EventBus`, and a capability that has something to announce declares its own type and sends it, the way physics sends `CollisionEvent` and animation sends `AnimationFinished`. A game reads it with `EventReader<T>`.
- The five render extension points are not on `App`: `RenderAppExt` in `nightshade_wgpu::commands` carries them, `App` holds the table in one type-erased slot, and `nightshade_wgpu::commands::into_parts` takes it back out as three values, the world, the host that drives the schedules, and the render hooks the backend keeps. A graph config hook takes the graph and one `PassBuild`, which carries the device, the queue, the shader composer, the four formats, the render buffer size, the bindless caps and `targets`, the whole `RenderTargets` by reference. A pass names the target it reads as a field, so a target that is gone is a compile error rather than a lookup that returns nothing and an install that is skipped. A frame inputs hook takes the renderer and the frame description together, which is what a capability needs when it reads the frame and writes a value back into it, the way the geometry crate reads the atmosphere and writes the image based lighting blend. They cannot be a resource, because the resource map wants `Send + Sync` and the `IntoPreRenderSystem` arms would have to carry that bound through every `ExtractParam::State`.
- Every crate under `crates/plugins/` carries a plugin, and `just lint-dag` fails on one that does not, because a plugin is what a composable engine piece is: `PlatformPlugin` inserts the five platform resources and registers the whole input frame contract, the five resets, the clearing of the input event list, the cursor the frame asks for and the recentring of a locked cursor, so a program that sets a runner of its own keeps all of it, `ScenePlugin` inserts `EntityRegistry` and `TransformState` and registers the propagation pass, `GraphicsPlugin` inserts the nineteen render resources and registers the sixteen frame systems over them, the scene sync and the material sync included, and `RenderPlugin` composes graphics. `WindowPlugin` composes the platform, the scene and the engine's actions, so composition order does not matter. A crate that stands on its own and names no engine is not a capability and does not sit there: `crates/support/` holds those, `nightshade-load`, `nightshade-store`, `nightshade-texture` and `nightshade-worker`, each a tool a plugin composes, and `just lint-dag` fails on a support crate that names `nightshade`. Capability crates live at `crates/plugins/`, in four levels a crate may only name downward: `describe/` is the vocabulary every other crate speaks and holds the `nightshade-platform`, `nightshade-scene`, `nightshade-render`, `nightshade-text` and `nightshade-paint` chain beside `nightshade-state` and `nightshade-steam`, which name the ECS and nothing else, `domain/` holds one capability each, `compose/` holds the five roots that run a loop or own a backend, `nightshade-openxr`, `nightshade-ui`, `nightshade-vulkan`, `nightshade-wgpu` and `nightshade-window`, and `draw/` holds what builds on a backend, the capability passes beside `nightshade-app` and `nightshade-wgpu-geometry`, which carries the sky, the shadow depth, the mesh, the skinned mesh and the scene overlay over the wgpu backend and publishes the nine shader modules those passes import. `nightshade-wgpu-outline` is the same shape for the edge a marked entity draws, so no capability is left inside the backend behind a feature flag. The sky and the image based lighting are `nightshade-wgpu-sky`, the text is `nightshade-wgpu-text`, and the developer lines and the ground grid are `nightshade-wgpu-debug`. The last three draw inside the scene overlay's shared render pass through `OverlaySubPass`, which the geometry crate publishes and which particles already used, so a capability that draws over the scene needs no attachment of its own. Each registers with `add_render_graph_sub_pass`, a second graph band the backend runs after every pass is installed, so the overlay is there whatever order the program composed the plugins in. `nightshade-wgpu-shading` is that vocabulary as a crate of its own: it publishes the nine shader modules every lit pass imports, in a phase the backend runs before any graph config hook, so no capability has to be composed before another to have its imports resolve. It shows a `backend` module the way the other draw crates do, and `just lint-dag` holds every crate that publishes one, so a consumer names what the list carries rather than the crate's own module tree. Beside them it holds the Rust the same passes share, the light cluster grid, the area light tables, the material bind group builders, the scene uniforms, the shadow projections and buffers, the fog and the occlusion culling. `nightshade-wgpu-shadow` draws the depth every shadow reads from. What is left in `nightshade-wgpu-geometry` is the mesh, the skinned mesh and the overlay that hosts what draws over them. An install that cannot place its pass panics naming the pass, because a capability that composes and draws nothing is worse than one that stops. The four come from the crate graph rather than from taste, and under them no edge points up. A crate outside `compose/` never takes a sibling's `plugin` feature, and one such edge is left in the tree. `nightshade` holds no plugin of its own. Nothing publishes: every crate carries `publish = false`.
- `crates/framework/` is the level between the plugin crates and the apps, and it is grouped one directory deep by what a crate is allowed to name. The four groups run `base`, `mechanics`, `interface`, `tools`, a crate names only a group below its own, and outside `base` it never names a crate in its own group, because a mechanic that reads a sibling would need an order against it. `just lint-dag` fails on both. `base/` names nothing but a leaf dependency and holds the pure values everything else measures with: `nightshade-plane`, which says whether a game plays on the ground or from the side and carries `flatten`, `raise`, `across`, `lift` and `move_across` over it, beside `nightshade-ease`, `nightshade-noise`, `nightshade-random`, which is the seeded generator every game draws its scatter and its coin flips from, and `nightshade-kit`, which holds the models, the sounds and the icons a game builds its world from, with the bytes at `assets/kits/`. `base/` also holds the questions a mechanic asks the world through: `nightshade-ground` for height and solidity in a continuous world, `nightshade-cells` for a cell in a discrete one, and `nightshade-arc` for whether a target stands inside the arc a swing covers. Each is a table of function pointers the game fills, so a mechanic asks without knowing what answers, and an answer takes the rows and never the resource map, because a signature that names `Res<Time>` must not take the whole map back through a type alias. It holds the values a game and its mechanics both read as well, `nightshade-clock`, `nightshade-story` and `nightshade-inventory`. `mechanics/` holds one game mechanic each, `nightshade-pickup` and `nightshade-daynight` among them, `interface/` holds what draws, and `tools/` holds what only a developer runs. A mechanic crate carries no tuning constant: it takes a settings resource the game inserts, which is what lets six games keep six different numbers. A mechanic announces what happened and never reads another mechanic's state, so nothing needs an order against a sibling, and a mechanic picks a stage rather than an order: `First` turns input into intent, `Update` decides and asks, `LateUpdate` resolves world state with one writer for each value, and `FrameUpdate` reacts to what this frame settled. A system that writes the window title belongs in `Update`, because a window call from inside the frame stages waits on the thread that owns the event loop. Three rules hold the level: every crate carries a working example and something that names it, an engine or plugin crate never takes a framework crate, and a game that needs a shape a framework crate already carries takes that crate rather than writing it again. A crate that nothing names is taken away, which is what happened to twenty-seven of them, so the tier is forty-six crates and every one has a reader. `just lint-dag` fails on a framework crate with no `examples/` directory, on a plugin or framework crate with no `README.md`, and on a crate named `nightshade-ui-<name>` that does not take `nightshade-ui`, because the prefix says what a crate builds on. `nightshade-readout` writes the window title, so it does not take the prefix. A framework crate keeps the shape of a plugin crate, the bands of `template/` and a plain `nightshade-<domain>` name. Every framework crate carries its own example at `examples/<name>/`, run with `just example <name>`, and a person drives it rather than watching it run: the example turns a key into an ask, the crate does the work, and the readout keeps to state. `just lint-examples` fails when an example stands in for the crate it shows, on three counts: a component the crate queries that the example never sets, so that system never runs, a value the crate works out that the example never reads back, and a settings struct built again beside the one the plugin inserted.
- There are fifty-four plugin crates, each carrying a plugin and each depending on `nightshade` while `nightshade` depends on none of them: `acoustics`, `animation`, `app`, `audio`, `camera`, `camera-controller`, `cli`, `config`, `decals`, `gamepad`, `gltf`, `graphics`, `input`, `log`, `navmesh`, `net`, `openxr`, `paint`, `particles`, `physics`, `picking`, `platform`, `portal`, `prefab`, `render`, `save`, `scene`, `sdf`, `sprite`, `state`, `steam`, `text`, `ui`, `voxels`, `vulkan`, `wgpu`, and `window`. Four tools sit at `crates/support/` instead, `nightshade-load`, `nightshade-store`, `nightshade-texture` and `nightshade-worker`, because each stands on its own and a plugin composes it. The menu, the settings panel, the shell and the test driver moved up to `crates/framework/`, because a crate that draws or tests is not a capability of the engine. `nightshade-app` is the composition every program repeats: it builds the `App`, sets the backend group from its own `wgpu` and `vulkan` features, writes the title, the capture frame, the window size and the frame pacing from one `Opening`, so a program says what it is and then adds only what is its own. The support crates take no `nightshade` at all. `nightshade-worker` is a crew of threads over a job trait, and a caller names its own key, result, and per worker tools. `nightshade-net` is a topic broker and its clients over TCP and UDP, and a caller names its own messages, so the crate moves them without knowing what they mean. `NetPlugin` opens the wire from one `WireSettings`, inserts it as a resource, and owns the thread and the two queues the frame reads, so a game publishes bytes on a topic and takes what arrived. `nightshade-store` has no ECS in it either: it is one pair of calls over whatever the platform keeps files in, a file below the system's data folder on a desktop, a file below the folder the activity was handed on android, and local storage in a browser, so a program that saves names a folder and a file and does not name a platform. `nightshade-save` is the document above it: a game names the folder, the format and the version on one trait, and the crate writes a header line in front of the payload, reads a slot back, lists the slots with their headers for a load screen, and takes one away. `SavePlugin::every(seconds)` inserts the `Autosave` clock and registers the system that announces `SaveDue` on the bus, for a period, an ask, or the window closing, so a game writes its payload when it hears rather than ticking a clock of its own. A file whose name or version the program cannot read reports nothing rather than a value that is wrong, and the payload stays the game's, as JSON or as bincode. A file an older build wrote goes through `Save::migrate`, whose default body decodes it as the current shape, and `Autosave` is the clock a game ticks to decide when to write. `nightshade-config` is the settings a program declares rather than the constants it scatters: `config!` writes an enum whose variants name the settings and a table of defaults, ranges and choices beside it, `Config<S>` holds the values a system reads, and `ConfigPlugin::<S>::new().persist(folder, name)` reads the file at startup and writes it back through `nightshade-store` when a value changes. `nightshade-ui-config`, which now sits at `crates/framework/interface/`, builds a panel from that same table and writes back what a person changes, so a settings screen follows the declaration rather than repeating it. `apps/features/settings` is the live example. `nightshade-input` is the one input layer: a program declares the actions a person can ask for as an enum that implements `Action`, each with its default keys, pointer buttons, pad buttons, sticks, triggers or press pairs, composes `InputPlugin::<Ask>`, and its systems take `Res<Actions<Ask>>` and ask `pressed`, `just_pressed`, `just_released`, `axis` and `axis2`. `Bindings<Ask>` holds named profiles that `bind`, `bind_only`, `unbind`, `wear` and `forget` change, and `persist(folder, name)` keeps them through `nightshade-store`. `EngineAction` is the engine's own set, which `WindowPlugin` composes, so the camera controllers, the physics character and the interface navigation read `Actions<EngineAction>` and no crate reads a key by name. `just lint-dag` fails on a game that does, apart from what `tools/dag-check/raw-input.txt` records. `apps/features/actions` is the live example. `nightshade-platform` and `nightshade-scene` are plugin crates like the rest, and twenty crates take one or both with `default-features = false` and its `contract` feature, so naming a window or a transform never links the behavior behind it. No capability is left in the engine.
- A plugin crate that needs another declares it by path with `default-features = false` and enables only its `contract` feature, never its `plugin`, so it gets the types and never the other capability's behavior. The composition roots are the exception: `nightshade-window`, `nightshade-ui`, `nightshade-graphics`, and `nightshade-prefab` take the `plugin` feature of the scene, the platform, the camera or the text to compose or drive it, and every such edge is recorded in `tools/dag-check/plugin-edges.txt`, which `dag-check` reads so a capability crate cannot add a `plugin` edge unseen. Cargo refuses `default-features = false` on an inherited workspace dependency, which is why the edge is declared by path. Sixty-four exist, and every one is a contract: `nightshade-physics` takes the picking contract for its trimesh ray results, `nightshade-gltf` the animation contract to build clips and `nightshade-worker` for the crew that reads a model off the frame, `nightshade-wgpu` and `nightshade-ui` the text contract for the glyph meshes and the string cache, `nightshade-openxr` and `nightshade-picking` the camera contract, and almost every plugin crate takes the scene and platform contracts for the node vocabulary and the window and input types. `nightshade-render` needs no such treatment, because it is all contract already, so a crate that reads the render description takes it whole. A plugin crate takes another whole only where the other carries no `contract` feature to ask for. Six are taken that way today, `nightshade-graphics`, `nightshade-window`, `nightshade-ui`, `nightshade-wgpu`, `nightshade-prefab`, and `nightshade-store`, and each of the first four carries a plugin that rides along. `just lint-dag` cannot see those edges, because it asks for `contract` only where `contract` exists. The program composes both plugins when it wants both to run. A plugin crate that needs another takes it with `default-features = false`, so it gets the contract types and never the other plugin.
- A plugin crate splits at a feature the way `template/` does: `contract` for the types another crate speaks, with no dependency at all, and `plugin` for the systems and the engine. The module layout is the same in every plugin crate and `just lint-dag` fails on a cycle between the bands: per-entity data in `components`, shared data in `resources`, plain values and lookup tables in `data`, frame behavior in `src/systems/`, functions that change a resource in `commands`, functions that only report in `queries`, and `plugin.rs` registering and nothing else. What sits outside the layout is render graph plumbing and assets: the openxr device and runner, the winit runner and the platform icon in `nightshade-window`, and the private `renderer` module in `nightshade-wgpu`. `src/plugins/` is gone. A plugin crate registers its own systems and installs its own resources. No crate registers another crate's system. `WindowPlugin` is `nightshade-window`, `RenderPlugin` is `nightshade-wgpu`, and `LogPlugin` is `nightshade-log`.
- `nightshade-wgpu` carries no `contract` feature, because `nightshade-render` is its contract. It is the GPU backend and nothing else: its `renderer` module is private and it shows two paths, `nightshade_wgpu::wgpu` for the GPU API and `nightshade_wgpu::backend` for the render graph, the passes, and the install points. `backend` is a list rather than a re-export of the whole renderer, so the pass tree is not public API and `just lint-dag` fails when a crate names a path the list does not carry. A second backend is a sibling crate with the same two paths, reading the same frame description out of `nightshade-render`, and `nightshade-vulkan` is that sibling: it shows `nightshade_vulkan::ash` and `nightshade_vulkan::backend`, drives an ordered pass list over Vulkan 1.3 dynamic rendering rather than mirroring the wgpu graph, and exists for the task and mesh shaders WGSL cannot express. It carries its own `RenderPlugin` and its own `VulkanAppExt`, so a program composes one backend and the hook names differ enough that importing both is a compile error rather than a silent clash.
- Proximity runs on the GPU. `nightshade-near` names no GPU API: an entity joins the grid by carrying `Bulk`, an entity the crowd holds apart carries `Crowded`, a game asks with `ask_what_is_near` under a tag it owns, and `NearPlugin` gathers the points in `Stage::Render`. The backend owns the work: one compute pass clears a bucket grid, fills it by atomic append, answers every ask, and works out the push for every crowded body, then copies the answers into a staging buffer and maps it without blocking. The answers in `NearAnswers` are the answers to the asks of the frame before, the way a GPU pick comes back after the click, and nothing waits on the device. `nightshade-acoustics` is the same shape, a grid and a readback off a `pre_render` hook with no graph node, and `apps/features/boids_gpu` is the shape where nothing comes back at all.
- The engine renders reverse-Z, so a backend clears depth to zero and compares with `GREATER_OR_EQUAL`. Every capability that draws does the same: the retained UI publishes a `PaintFrame` into `nightshade-paint`, decals publish a `DecalFrame`, particles publish a `ParticleFrame`, sprites publish a `SpriteFrame`, and signed distance fields publish an `SdfFrame`, each gathered by a plain system in `Stage::Render`. The backend takes those contracts, owns every pass and every shader, installs them itself, and reads the frames in its pre-render hooks. No capability crate names a GPU API, so adding a backend touches one crate.
- No engine feature gates behavior any more: the glTF import, the prefab spawn, and the texture upload pipeline are always there. The import and the spawn are two crates: `nightshade-prefab` holds what a prefab is and how it becomes rows, and knows no file format, while `nightshade-gltf` reads glTF into the `ModelImport` the spawner takes, owns the worker crew and the web fetch that bring a model in, and carries `GltfPlugin`. A program that reads a model names `nightshade-gltf`, and one that only spawns a prefab it already holds names `nightshade-prefab`. A capability the program never names costs nothing and links nothing. Plugins do not reference each other.
- A capability that has to say something to another publishes the data for it in its own `src/contract.rs`: types and nothing else, behind the `contract` feature, which pulls in no `nightshade`, so naming the ask never links the answer. The asker takes that crate with `default-features = false` and `features = ["contract"]`, and never its `plugin`. An ask about an entity goes there as a component the owner picks up by archetype and takes off, not as a queue: `PendingSound` on the entity to be heard, `PendingCameraMove` on the camera to be turned. A component works because a frame runs between the ask and the answer. Where the caller must see the result before its own call returns, a capability appends a function to one of the assembly band's tables instead: `RetainedUiSchedule` for the UI pipeline, and the render graph's pass hooks. Those two are the whole set, and a third has to meet the same test: the work lands inside one synchronous call, and the table's owner names no capability. Each runner reads one pointer out of its table at a time rather than holding the table across the call, so a hook that spawns a prefab of its own still sees the whole table. A plugin crate declares the edge in Cargo: `nightshade-physics` names `nightshade-picking` by path with `default-features = false` and puts `nightshade-picking/contract` in its own `contract`, so building physics as data builds picking as data too.
- `just lint-dag` fails on any other cross-plugin reference, on a module cycle inside any engine or plugin crate, on a `nightshade_wgpu::backend` path the backend list does not carry, on a bare `nightshade_ecs::World` built outside a test, and on a `plugin`-feature edge that `tools/dag-check/plugin-edges.txt` does not record. It fails on a crate that declares a `contract` feature its crate root gates nothing behind, and on a contract edge whose consumer names a module the other crate keeps behind its `plugin`, which is how a crate calls another capability's behavior through a manifest line written in the approved form. It holds the levels: a plugin crate sits in one of `describe/`, `domain/`, `compose/` or `draw/`, names only a level below its own, and outside `compose/` never takes a sibling's `plugin`. It holds the backend the same way: only a crate under `draw/` or `compose/` may name `nightshade-wgpu` or `nightshade-vulkan`, because a backend carries no `contract` feature, so naming it links the whole renderer, and every other crate reads the frame description through `nightshade-render`. It fails on a crate under `crates/plugins/` with no `plugin.rs`, and on a crate under `crates/support/` that names `nightshade`, which is the pair of rules that says what a plugin crate is. It holds the bands themselves: a plugin crate may declare only the modules `template/` carries, a `plugin.rs` may hold only its plugin struct, that struct's `Plugin` impl and functions named `install`, `register` or `initialize`, a query must report and must take nothing it can change, and a command must change something. Each of those four carries a ledger at `tools/dag-check/`, `module-exceptions.txt`, `silent-queries.txt`, `query-mutations.txt` and `command-reports.txt`, and each list only shrinks, because the check fails on a line naming a function that is gone or already clean. A function that returns `Result` is doing something outside the ECS, so it never joins the command list. `just new-plugin <name> <level>` writes a crate on those bands at that level so a new one cannot start the wrong shape, and `just check-crate <name>` shows only the faults naming one crate, which is how a crate is checked while it is still small. It also fails on an app component that gathers two or more named values, and on an empty marker, apart from the apps `tools/dag-check/component-sweep.txt` still records. That list only shrinks, and the check fails on a line naming an app that is already clean. It also fails on a file that calls a method on `window.handle` and is not recorded in `tools/dag-check/window-handle.txt`, which holds the runner, the backends that build a surface at startup, and the systems that name the `MainThread` parameter, because a platform routes a window call to the thread that owns the event loop and waits for it to arrive. What keeps a contract honest is the compiler rather than a lint: `just lint-features` builds every crate that splits with `--no-default-features --features contract`, so a contract module that reaches for a world, a system, or another capability fails to build. Fourteen plugin crates do not split, because nothing asks them for types or because the whole crate is already the contract: `nightshade-app`, `nightshade-cli`, `nightshade-gltf`, `nightshade-log`, `nightshade-net`, `nightshade-paint`, `nightshade-render`, `nightshade-save`, `nightshade-steam`, `nightshade-ui`, `nightshade-vulkan`, `nightshade-wgpu`, `nightshade-window`, and `nightshade-prefab`, whose node types name the render schema and so cannot compile without it. The framework tier splits at one crate, `nightshade-countdown`, and every other crate there is already all contract.
- A crate reaches the ECS through `nightshade::ecs`, which is `nightshade` re-exporting `nightshade-ecs`, so a plugin declares one engine dependency rather than two. Fifteen crates still declare `nightshade-ecs` directly and each has a reason the compiler enforces: most speak about entities from their contract, which by design has no `nightshade` to reach through, and `nightshade-wgpu` forwards an ECS feature (`parallel`, `profiling`) rather than naming a type. Every other crate names `nightshade::ecs`.
- A plugin module reaches the engine through `App::insert_resource`, `add_render_graph_config`, `add_render_graph_sub_pass`, `on_update_render_graph`, `on_pre_render`, `on_frame_inputs`, `on_window_event`, and `set_runner`. `on_pre_render` takes a system rather than a closure over borrows: it names `pre_render::Renderer` first, then the `Res`, `ResMut`, and one `Query` it reads, and the runner takes one disjoint borrow per resource the signature names. The resource parameters resolve against the resource map, which is its own `ResourceHost`, so `State::pre_render` still takes the rows and the resources rather than a world. What that costs is `Commands` and the event parameters, which need a host carrying the allocator and the bus. The band runs its hooks in registration order and does not batch them, so the signature buys the reader and the repeat check rather than parallelism. The renderer sits in a fixed first position instead of resolving out of a host, because every `IntoSystem` impl requires a `'static` host and a band holding a `&mut WgpuRenderer` has none to offer. A domain that draws places its own pass with `install_scene_pass` (end of the scene), `install_lit_pass` (over the lit meshes, under the overlay), or `add_overlay_sub_pass` (inside the overlay's shared render pass, which is how particles avoid a second attachment round trip, and which is registered in the sub-pass band so the overlay is already installed), then reaches it each frame with `render_graph_get_pass_mut` plus a downcast. The backend also carries the descriptor vocabulary every pass builds through, published as `nightshade_wgpu::backend::build`: the bind group layout entries, the bind groups, the buffers, the samplers, the textures, the depth and blend states, and `Pipe` for a render pipeline. The order of the frame is one rule and the graph derives nothing from it: a pass runs in the band its `PassPosition` names, and two passes in the same band run in the order they were installed. `render_graph_build_dependency_edges` walks the passes in that order and only ever draws an edge from an earlier pass to a later one, so the topological sort confirms the order rather than finding it. What the graph works out for itself is the resources: the load and store operation of every attachment, from the first write and the last read across the frame, and the pooling of the eighteen transient textures by lifetime. `add_plugin` builds a type at most once and drops a duplicate rather than panicking. A plugin says what it cannot install itself with `fn needs`, which returns the resources it reads and the plugin each one comes from, written with the `needs!` macro, and `App::run` checks the whole list before the first frame and panics naming every missing resource and the plugin that installs it. That is what keeps a capability from installing another capability's resource to stop its own systems from panicking. `nightshade` holds only the substrate. `App::set_runner` lets a plugin own the main loop itself, which is how a host drives the composed App from a loop of its own. It is a claimed slot: the caller names itself, and a second claim panics with both names rather than replacing the first, so `take_over_runner` is what a program calls when the replacement is the point, the way `nightshade-openxr` takes the loop over from the backend it composed and the multiplayer sandbox takes it over to serve with no window. `nightshade-window` names no backend: it holds the winit loop and two traits, `Host` for the three backend-free calls (initialize, run_systems, window_event) and `Renderer` for the four the frame needs (configure, resize, update, prepare, render), neither of which names a GPU type. `nightshade-wgpu` implements both and sets the runner, so a second backend is a sibling implementing the same four methods.
- ECS via `nightshade_ecs`. There is one `World`, `{ storage, events, resources }`, and it holds every component: the renderer's, the retained UI's, each composed capability's, and the game's. Nothing declares a component. Any `Send + Sync + Default + 'static` type is one, and the first write of it appends it to the world's schema and takes the next of 256 mask bits, which components and tags take from together, and the ECS reports a warning when fewer than 32 are left, so no crate registers, marks, or lists its component types and there is no schema to keep in order. The ECS is runtime storage and has no serialization at all: a game that saves writes its own format over the data it authored. Nothing names a mask slot either: every selection API takes the component types as a generic bundle tuple (`query_entities::<(Camera, LocalTransform)>()`, one-element tuples keep their trailing comma, `()` means no components).
- Typed access is by component type: `world.get::<Camera>(entity)` / `world.get_mut::<T>` / `world.set(entity, value)` / `world.has::<T>` (get_mut and set stamp change ticks; set takes a slot for a type the world has not seen). `World` derefs to its `storage`, so spawn_count, despawn_entities, despawn_recursive, and is_alive are called on `world` directly; `world.spawn((component, ...))` is the default single-entity spawn, deriving the archetype from the component types, with `world.spawn_entities::<(Name, LocalTransform)>(count)` for batches and all-default rows. `world.storage` names the storage itself for world-level operations: pinned queries, ticks, structural logs, and raw table passes. Singletons live in `world.resources`, the ECS resource map, rather than on a struct an app owns. Read one with `world.res::<T>()`, write it with `world.res_mut::<T>()`, or take it as a `Res<T>` / `ResMut<T>` system parameter. Both accessors panic when the resource is absent, so a capability whose plugin was never composed fails loudly rather than silently doing nothing.
- Most engine systems run automatically in the frame stages (`Stage::FrameStart`, `Stage::FrameUpdate`, `Stage::FramePostUpdate`, `Stage::Render`, `Stage::Last`) that follow the game stages each frame in one `Stages` run: the core systems (animation, transforms, input) land first and each composed plugin registers its own (physics, navmesh, retained UI, render sync) with `app.add_system(Stage::..., system)`; within a stage, systems run in registration order. Don't call these manually.
- Camera controllers are opt-in: call `fly_camera_system(world)` or `pan_orbit_camera_system(world)` from your update system. `fly_camera_system` skips if the active camera carries `PanOrbitCamera`.
- Scenes load from glTF. Find entities by name after spawning (`world.find_entity_by_name`).
- The command line is `nightshade-cli`: an app declares its own arguments as a `#[derive(clap::Args, Default)]` struct in `resources.rs`, with `use nightshade_cli::clap;` for the derive and `#[arg(help = "...")]` for the help text, never a doc comment. Every app composes `CliPlugin::<Arguments>::default()` right after `WindowPlugin`, and `CliPlugin::<NoArguments>` when it has no flags of its own. The plugin writes the window and the scheduled capture, so composing it before `WindowPlugin` fails an assertion that says so. The plugin parses once, inserts the struct as a resource, and fills the engine's `ScheduledCapture` and the window size from the flags every app shares: `--capture <path>`, `--capture-next <path>`, `--capture-frame <n>`, `--capture-settle <n>`, and `--size WxH`. A plugin composed after it may read the struct in `build`; a system reads it as `Res<Arguments>`. On the web the same fields come from the URL query string, read from the window or from a worker's own scope. On android an argument list that clap rejects falls back to the defaults rather than closing the app. `capture_frame` on the plugin is the frame the picture is taken on when the flag does not say, which an app raises when its scene takes longer to settle.
- `apps/games/tower_defense` is the go-to reference for an idiomatic engine-level 3D game. Read it before writing a new engine-layer app: a game plugin added in the App builder registering startup and update systems that name their parameters, its own game components, screens driven by app states, retained UI handles stored in a plain resources struct. `apps/games/coin_rush` is the same architecture at a smaller size, with the `components`/`resources`/`systems`/`theme` layout laid out plainly, and the `template/` crate is that layout in skeleton form. To see one renderer capability on its own, read the app in `apps/rendering/` that carries its name, or in `apps/vulkan/` when only that backend can draw it: each composes a backend, brings in the Khronos sample model the feature is visible on, and says in its README what to look for.

## Querying

- Default: typed tuple queries. `world.query_ref::<(&RenderMesh, &MaterialRef)>().iter()` for reads (a real iterator on `&world`, never registers types), `query::<(&mut A, &B)>().for_each(...)` for writes (`&mut` elements stamp change ticks per visited row, so take `&mut` only for what you actually write). Filters: `.with::<T>()` / `.without::<T>()` / `.changed::<T>()` / `.added::<T>()`. Up to eight elements, `Option<&T>` for optional presence.
- Bulk visit-don't-write passes stay on the raw tier (`for_each_mut::<(LocalTransform,), ()>(|entity, table, index| ...)`, an include bundle and an exclude bundle, `()` excludes nothing) with `table.column_mut(key)`, keys from `component_key::<T>()`. The raw tier does not stamp ticks, so pair it with explicit side-channel marks or per-table `table.mark_column_changed(key, tick)`.
- Entity-only iteration: `query_entities::<(RenderMesh, MaterialRef)>()` (allocation-free iterator), `query_entities_changed_since::<(T,)>(tick)` for the changed form.
- Presence tests take the same bundles: `entity_has_components::<(A, B)>(entity)` for all of them, `entity_has_any::<(A, B)>(entity)` for at least one, `change_touches::<(A, B)>(&change)` for a structural log entry. `clear_components(entity)` strips the entity's whole row in that world. A read and a removal read a bundle's mask differently: a read that names a component the world has never been written matches nothing, because a missing element would widen the match rather than narrow it, while a removal drops that element and takes the rest.
- For structural mutations during iteration (add/remove components, despawn, set component triggering archetype migration), use the two-pass pattern: gather into a small `Vec` of `(entity, payload)` tuples, then a second loop that applies the mutations.
- Two command queues at `world.res::<CommandQueues>()`: `commands.ecs` (DespawnRecursive, ReloadMaterial) is drained by `process_commands_system` in the frame schedule. `commands.render` (texture uploads, HDR skybox, IBL captures, screenshot) is drained by the renderer at frame setup. Push via `queue_ecs_command(world, EcsCommand::...)` or `queue_render_command(world, RenderCommand::...)` (free fns in the prelude, not methods).

## Game Components

A game component is the struct that declares it and nothing else. Writing one takes a mask slot, so an app registers nothing and `components.rs` holds no registration function. A game that saves its state writes its own format for it, not the ECS. Game state is set directly on the engine entity (`world.set(entity, component)` creates the row), read back with typed queries, and one recursive despawn tears down render and game state together. App-wide state lives in a plain resources struct the game plugin inserts with `app.insert_resource(...)`, the way `TowerDefenseResources` is inserted in `apps/games/tower_defense/src/plugin.rs`. There is no link component and no position sync pass; write `LocalTransform` through `world.get_mut` directly. Marker tags (selection, locked, in-hand) take a mask bit from the top of the same 256 that components take from the bottom, and what they save is the column and the migration: `world.add_tag_type::<T>(entity)` / `remove_tag_type` / `has_tag_type` / `query_tag_type`, dropped on despawn; filter typed queries with `.with_tag_set(world.tag_set_type::<T>()...)`. A tuple mixing game state with an engine transform is one ordinary query, because they are all components of the same world. `template/` is the starting point to copy, and `template/src/components.rs` is where a game's own components go.

## Gotchas

- WGSL uniform structs need 16-byte alignment. Use `vec4` packing, not `vec3`.
- `nalgebra_glm` only, never `glam`. `Vec2::component_mul()` for element-wise multiply.
- Every engine world comes from `nightshade_ecs::World::tracking()`, which turns on change detection and the structural log. A bare `World::new()` records neither, so every consumer that reads the world by diffing it reads an empty set: transform propagation runs one pass and stops, and the scene freezes after its first frame. `just lint-dag` fails on a bare world built outside a test.
- The renderer syncs by diffing nightshade_ecs change ticks, and raw-tier table writes (`for_each_mut`, `column_mut`) do not stamp them. Write every render-facing component (transforms, visibility, lights, morph weights, text, instanced meshes) through the stamping paths (`set`, `get_mut::<T>`, or `&mut` typed-query elements) or the change never reaches the renderer. Raw-tier bulk passes can opt in afterward with per-table `table.mark_column_changed(key, tick)`, one call per component with a `ComponentKey<T>` from `world.component_key::<T>()`. Mutate registered materials through `material_registry_mutate`.
- `nightshade_ecs::Entity` is the entity type everywhere.
- Sprites are `nightshade-sprite`: an app packs pictures into a named atlas with `sprite_atlas_create` and `sprite_atlas_insert`, and a `Sprite`, a `SpriteAnimator`, or a `Tilemap` on an ordinary transform entity is gathered into the `SpriteFrame`. Both backends draw that frame after the lit meshes, sorted by layer, then depth, then Y, tested against the scene depth without writing it: the wgpu backend as a lit pass over the scene color and depth, and the Vulkan backend as a scene pass that draws in the scope over the solids, with the atlases as images the pass owns and fills from the frame's uploads. `apps/features/sprites` is the flat reference, a tilemap farm under an orthographic camera, and `apps/games/farm` is the 2.5D one, a farm village of upright sprites on a block world under a tilted perspective camera, with the engine's day and night cycle driving the sun, the grading, the fog, and the lanterns, rain, block houses with lit windows, a tool hotbar with icons uploaded to the retained UI's image store, crops, three shops, errands, ten villagers on a daily schedule, and particle fireflies and fireworks. Its bands follow `template/`: types in components and resources, lookup tables in data, helpers in commands and queries, behavior in systems, and no comments. A flat shadow blob centered on a sprite's feet hides behind its body from a tilted camera, so put the blob forward of the feet, and a camera that looks down never sees the sky, so give it a horizon the fog can paint. A sheet packed on a grid gives every picture the same square cell, so an upright sprite reads its trim from `tile_trim` and cuts the cell down with `standing_tile`, which keeps the paint on its feet rather than floating over them. `Lifetime` on an entity is `nightshade-scene`, which despawns the entity when the count reaches zero, and `night_factor` over the day and night hour is `nightshade-render`.
- An `OrthographicCamera` with `x_mag: None` fits its width to the viewport; `matrix_with_aspect` is the path every consumer takes. A texture's `SamplerFilter::Nearest` reaches both backends through the packed slot's bit twenty.
